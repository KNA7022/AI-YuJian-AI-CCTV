# 单摄像头羽毛球场部署修改计划

编制日期：2026-09-13。代码基线：`main` / `cccfc57bdd37749fbe66f069dbf893c1faf365e1`。

本计划基于实际源码、现有球场部署需求文档和用户提供的摄像头截图。需求文档用于理解设计意图，不代表其中的功能已经实现。本次完成仓库拉取与方案分析，未安装依赖、连接摄像头、运行模型或修改业务代码。

## 1. 结论与首版范围

可以在现有项目上改造成单摄像头、单球场、本地运行的羽毛球分析系统，继续复用 Python 分析管线、FastAPI、React、SQLite、四点标定和结果导出。

推荐先完成：摄像头配置、实时取帧、持久化标定、手动开始/停止一场分析、球员姿态与移动统计、带标注预览、录像和历史结果。羽毛球检测作为单独可验证的能力；现场效果不足时明确显示不可用或低置信度，不把球员分析一并阻塞。

第一轮以现有的单打双人分析为基线，并在界面明确范围。双打需要另行完成四人持续 ID 跟踪，不能把现有上下半场统计当作四名球员的统计。自动回合识别先做辅助提示和人工修正；击球动作分类、自动计分、准确落点/压线判罚不作为首版交付承诺。

## 4. 推荐结构

```text
固定网络摄像头
    │ RTSP（优先验证 TCP 传输）
    ▼
取流/解码进程 ───────► 原始录像分片 + 分片索引
    │ 最新帧、有界缓冲、时间戳
    ▼
分析工作进程：姿态 → 球员跟踪 → 羽毛球检测 → 球场映射 → 统计
    ├── 最新带标注帧 → API 预览 → 浏览器
    ├── 状态与统计事件 → API SSE → 浏览器
    └── JSONL / 标注录像 / 会话摘要 / 热力图

FastAPI + SQLite：摄像头配置、标定、启停、历史、健康状态
```

实时预览使用只保留最新画面的策略，避免识别慢于输入时延迟持续增加；原始录像保持独立连续保存。两路并行取流时先验证设备允许的连接数，不允许则单路分流。分析帧必须带采集时间、源序号和丢帧信息，不能用处理帧数冒充源时间。

首版 AI 预览可使用低帧率 MJPEG，复用 SSE 传状态。它是单路本地 MVP 的实现选择，后续按带宽与延迟实测决定是否升级 WebRTC。不要把设备原始预览的低延迟等同于 AI 分析延迟。

羽毛球对连续帧更敏感，若实时采样率不足，应保留原视频供离线精分析，并把实时羽毛球轨迹标记为不完整。原始录像和可变采样的标注录像通过时间戳索引关联；标注录像应明确按时间重采样或采用支持时间戳的编码路径，避免简单按固定 FPS 写入造成快放及音画错位。

## 5. 实施步骤和验收

### P0：现场输入和性能基线（预计 1～2 个开发工作日）

1. 准备独立环境、FFmpeg、羽毛球与姿态模型。GPU 方案分别验证 PyTorch CUDA 与 ONNX provider；模型预下载并做启动检查。缺失羽毛球模型必须在页面明确提示。
2. 对截图提供的 RTSP 路径做有超时的探测，记录编码、分辨率、实际帧率、码率和时间戳稳定性；不要从播放器 KB/s 推断准确编码参数。
3. 固定机位覆盖四个场角、运动员脚部和高球区域，采集 5～10 分钟实拍素材，包含远近场、快速球、遮挡和实际灯光条件。分辨率先按设备实测确定，不为了预览流畅盲目降低羽毛球分析输入质量。
4. 分别跑人物、羽毛球、叠加与编码耗时，记录显存、处理 FPS 和画面年龄；以轻量模型作为 4GB 显存开发机的初始实验配置，不预先承诺 25/30 FPS 实时识别。

验收：能稳定取得可解码视频；能用现有离线流程完成一段现场视频分析；形成性能和可见度记录。若羽毛球在人眼逐帧查看时也难辨识，先调整机位/曝光/码流，再考虑训练模型。

### P1：流输入、持久化标定、可停止会话（预计 3～5 日）

- 新增 `badminton_analysis/media/frame_source.py`：统一文件/RTSP 的开关、读帧、超时和时间戳接口。取流放独立进程，阻塞读取可由监督进程终止和重建。
- 重构 `system.py` 的帧处理入口，输入帧及上下文，输出检测、统计和可视化结果；文件回放继续可用。
- 新增 `web/api/cameras.py`、`sessions.py`，扩展数据库，提供设备配置、抓图、标定、启停和状态查询。
- 标定从摄像头清晰帧生成；保存原始图像尺寸、四角点、机位标识、球场尺寸和版本。复用 `CalibrationCanvas.tsx`，验证点击顺序、凸四边形、边界和重复点。分辨率/裁切变化时阻止错误复用。
- 每个会话保存配置和标定快照，历史结果不随重新标定变化。明确 `preparing/running/reconnecting/stopping/stopped/failed/interrupted` 状态。

验收：浏览器完成配置、抓图和标定；重启后仍可复用；连续处理 30 分钟；停止操作可终止取流与推理并封存结果，不依赖等待无限流结束。

### P2：现场识别语义、实时页面和产物（预计 3～5 日）

- 新增 `CourtPage.tsx`、`LivePage.tsx`，调整路由与 API 客户端。页面展示原始/识别状态、标定状态、推理 FPS、丢帧、连接状态和启停按钮。
- 固定摄像头模式取消整帧模板匹配对推理的硬门控；新增异常画面检测作为健康状态，不直接计为比赛回合。
- 按时间戳修正速度/距离累计，过滤低质量位置和异常跳点，缺失期间不伪造轨迹；断流后断开轨迹，避免把恢复后的位移计入速度。距离仍为视觉估计值。
- 羽毛球数据写出置信度、检测/接受状态和缺失记录，避免将平滑轨迹等同于实际观测。ROI 留出高球区域，按实拍调整现有跳点和像素门限。
- 回合先支持人工标记；基于连续球运动与停顿的候选分段单独输出，经过现场标注验证后再启用自动统计。
- 按固定时长分片存储原视频和分析记录；停止后生成摘要、热力图和下载索引，原视频音频若需要则保留在录像路径，直播不走原有“结束时重新读取输入提取音频”的流程。

验收：至少人工检查 3 段代表性录像，记录人物漏检、身份切换、羽毛球漏检/误检和回合分段偏差；实时页面与导出使用相同时间线；重复读取统计不增加距离；暂停/断流不产生速度尖峰。准确率阈值在 P0 实拍标注基线后冻结，不用演示素材代替现场验收。

### P3：长期运行和部署包（预计 2～3 日）

- 明确心跳、超时及重连退避（例如 1、2、5、10 秒并设上限）。恢复后重新检查分辨率和标定，无法恢复时标记失败并封存已完成分片。
- API 和分析 worker 分进程管理；停止异常、模型异常均在 `finally` 回收资源。启动先处理残留运行状态再接收新会话，防止重复占用摄像头/GPU。
- 加入磁盘配额、分片保留规则和低磁盘保护，不能无限录像。容量以实际码率计算：仅视频每小时约为 `码率(Mbps) × 0.45 GB`，另留标注视频和数据空间。
- 增加启动脚本、配置示例、前端构建产物服务与开机启动说明；根据最终主机选择 Windows 或 Linux 的进程管理方式。
- 摄像头凭据独立保存在受限本地配置，API/日志脱敏；现有 `/storage` 静态公开目录不能存放凭据。校准摄像头时间，原始 URL 不写入导出元数据。截图暴露的默认凭据在现场部署时更换。

验收：完成 2 小时连续运行；插拔网络 30 秒再恢复，目标恢复后 30 秒内重新出图；模拟 worker 崩溃、重启、磁盘不足。已封存分片可读取、会话标为中断而不是成功；内存与显存无持续增长；实时画面年龄无持续积压。延迟目标先设 P95 ≤2 秒，在 P0 硬件实测后确认可实现的分辨率和分析帧率。

### P4：双打和羽毛球增强（后续单独估算）

双打需要四人跟踪、遮挡重关联、换边处理，连同 JSONL schema、统计、可视化和历史兼容一起修改。羽毛球若现场域差明显，再开展标注、微调或时序模型对比，使用独立测试片段评估，避免只看训练视频。

单目地面四点映射适用于球员地面位置估计；不能直接把空中羽毛球映射到地面后称为真实落点。准确落点、击球动作及裁判级判罚需额外方法和独立验证。

## 6. 交付顺序和工期边界

推荐按 P0 → P1 → P2 → P3 实施，每阶段留下能运行的结果。总计约 9～15 个开发工作日，是基于单路、单打基线的工程估算，不包含等待设备、现场重新安装、数据标注、模型训练或双打增强。P0 完成后依据真实码流和 GPU 基线调整排期。

首版交付：可启动服务、摄像头/球场配置页、标定页、实时分析页、会话历史与导出、恢复与存储保护、部署说明和现场验收记录。保持原有上传录像流程，并用同一现场视频对照文件与流模式的时间线和基本识别结果。
